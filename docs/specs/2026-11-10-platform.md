# Platform Spec — AWS Hosting and IaC (CDK)

**Status:** adopted 2026-11-10 (unit R0, jointly with LiteLLM L0). Built by
Phase 4R sub-phase **RP**. Replaces the Netlify hosting in
`docs/guides/dashboard-deployment.md` (decided 2026-11-09). Runs may write,
`cdk synth` and assert the CDK; **deploying is always a user action**.

## Overview

The dashboard runs on **AWS ECS Fargate**, for **private use only** inside
the company network and VPN. Design principle: **minimum resources** — reuse
what exists, create only what the dashboard cannot run without. Anything not
in *Created resources* needs an amendment to this spec first.

## Region

All stacks deploy to **`ap-southeast-2`**, the single source being
`COLLECTOR_REGION` in `packages/shared/src/region.ts` (Rule 50.7); the
dashboard reads the table in that region.

## Assumed to exist (never created)

- **VPC and private subnets** — imported by id.
- **Network routing through the existing Transit Gateway** — gives the
  subnets the egress Entra ID sign-in needs and access to AWS service
  endpoints. **No NAT gateway and no VPC endpoints are added**; an existing
  DynamoDB gateway endpoint may be named (*Data isolation*). If a
  deploy-time check shows a path missing, it is reported as a user action.
- **ACM certificate** — imported by ARN; none is requested.
- **LiteLLM** — already deployed and reachable internally; never deployed,
  configured or hosted here.

## Load balancer

- **Import mode** (an ALB HTTPS listener ARN is supplied): the DashboardServiceStack
  imports the listener, its ALB and its security group and adds only its own
  target group, one **host-based** listener rule (e.g.
  `llm-usage-lens.<company-domain>`) with a **unique priority** agreed with
  the ALB owner, the certificate as an extra SNI certificate only if the
  listener's does not cover the host, and one ingress rule on the task
  security group from the ALB security group on the container port. It never
  changes the ALB, the listener's default action, or other rules; undeploy
  removes only what it added. No ALB or target-group alarms are added (the
  existing ALB's own alarms cover it).
- **Create mode** (no ARN): one **internal** ALB (`internetFacing: false`)
  in the imported private subnets, one HTTPS listener with the imported
  certificate and a TLS 1.2+ policy, **no HTTP listener**, and a security
  group allowing 443 only from the supplied company CIDRs.
- **Both modes:** a plain `FargateService` attached to the listener — not
  `ApplicationLoadBalancedFargateService` or ECS Express Mode, which always
  create their own ALB.

## Data isolation

Amended 2026-11-14 (user): user data (identities, password users, SSO
references, memberships, grants, audit) must not be reachable by other
apps, services or principals in the account. The private subnets are
reachable from other subnets in the same account, so the network is not the
boundary on its own; every layer below is synthesised and asserted.

| Layer | Control |
|---|---|
| **Who may read or write the table** | A **table resource policy** (FoundationStack) with one `Deny` for `Principal: "*"` on the data-plane and export actions (`GetItem`, `BatchGetItem`, `Query`, `Scan`, `PutItem`, `UpdateItem`, `DeleteItem`, `BatchWriteItem`, `ConditionCheckItem`, `PartiQL*`, `ExportTableToPointInTime`, `RestoreTableToPointInTime`) unless `aws:PrincipalArn` is one of: the dashboard task role, the collector role (from Phase 6), and the optional `opsRoleArn`. It overrides any IAM grant, including administrators' `dynamodb:*`. Control-plane actions stay with IAM so CloudFormation can still manage the table. The roles are matched by ARN in a condition (not the `Principal` element), so the policy can name roles another stack creates later; the task role therefore has the fixed name `llm-usage-lens-<env>-task` |
| **Collector** | Its role (Phase 6) may write only cost keys (`ACCT#*`, `SYSTEM`) and read `ACCT#*`; it never reads identity, password-user, SSO, governance or audit items |
| **Network** | Optional `dynamodbVpcEndpointId` (an existing DynamoDB gateway endpoint; none is created): when set, the task role's access must also arrive through it (`aws:SourceVpce`), so its credentials are useless outside the VPC. Tasks have no public IP and accept traffic only from the ALB security group (*Load balancer*) |
| **Encryption key** | The CMK's key policy limits `kms:Decrypt` and `kms:GenerateDataKey` to the same roles (each granted to the account root and conditioned on `aws:PrincipalArn`, because KMS rejects a policy naming a role that does not exist yet when the FoundationStack deploys first; amended 2026-11-14) (through DynamoDB, plus the task role's envelope encryption of TOTP secrets), the execution role through SSM, and CloudWatch Logs for the audit group; the account root keeps key administration only. Account principals may also `kms:Encrypt` and `kms:GenerateDataKey` **through SSM only** (`kms:ViaService = ssm.<region>.amazonaws.com`) so operators can create and rotate the SecureStrings; that grant cannot decrypt existing ciphertext (amended 2026-11-14). Upgrading a deployment made before the fixed role names: deploy the DashboardServiceStack first, then the FoundationStack, or the new policies deny the running tasks' old auto-named role. The task environment carries `TOTP_KMS_KEY_ID` = the CMK ARN, required when `APP_ENV=prod`, for the envelope encryption of password users' TOTP secrets (amended 2026-11-14, R2b-2). Backups and exports are unreadable to anyone else |
| **Fields** | Password hashes only; TOTP secrets envelope-encrypted before storage (Access Control — *Password users*) |
| **Break-glass** | The `opsRoleArn` role is for incidents only (Operations runbook — *Break-glass data access*): MFA through IAM Identity Center, each use recorded with a reason, and its data access reviewed afterwards from CloudTrail **data events** on the table (a user action on the account trail, filtered to the table; a small per-event cost, accepted and documented in the runbook) |

Verification: the policy and key policy are asserted (exact principal
list, data-plane actions only); after the first `dev` deploy, a read with an
account administrator role that is not on the list must be refused (user
action, recorded in the deployment guide) before the policy goes to `prod`.

## Runtime

- **Credentials:** the task role through the default chain — no static keys
  (Rule 50.1).
- **Secrets:** the task definition's `secrets` (`valueFrom` SSM parameter
  ARNs) inject them at task start — `AUTH_SECRET`, the Entra client secret
  (only when Entra is configured),
  the master-user hash and TOTP secret, the LiteLLM service key. Application
  code never calls SSM.
- **Caching:** Next.js's cache is per task; nothing relies on cross-task
  invalidation. Only rollups are cached (per UTC day, hourly); authorization,
  Settings and LiteLLM data are read per request (Access Control —
  *Enforcement* item 4).
- **Health check:** the target group checks `/api/health` (no session;
  `{ data: { status: "ok" | "degraded", dependencies } }` — DynamoDB
  reachable, LiteLLM reachable when configured — no data). It always
  answers `200` while the process serves: a DynamoDB outage reports
  `degraded` instead of failing the check, so ECS does not replace every
  task in a loop (decided 2026-11-10, RP). The Auth.js proxy matcher
  excludes exactly `/api/health`.
- **Response security headers:** `next.config.ts` sets, on every response,
  `X-Frame-Options: DENY`, `Content-Security-Policy: frame-ancestors 'none'`,
  `X-Content-Type-Options: nosniff`,
  `Referrer-Policy: strict-origin-when-cross-origin`,
  `Strict-Transport-Security: max-age=31536000` (no `includeSubDomains` — the
  parent domain is not the dashboard's to pin) and
  `Permissions-Policy: camera=(), microphone=(), geolocation=()`; the
  `X-Powered-By` header is off. A script/style Content Security Policy is not
  in v1 ([future improvements](../future-improvements.md) — *Script and style
  Content Security Policy*). Decided 2026-11-11 (security review).

## Task role policy (least privilege)

Shared with the LiteLLM spec. Asserted with CDK `assertions`.

| Statement | Actions | Resource / condition |
|---|---|---|
| Reads | `GetItem`, `BatchGetItem`, `Query`, `DescribeTable` | The table and `index/GSI1` (the shipped index name, `GSI1_NAME`) |
| Writes | `PutItem`, `UpdateItem`, `DeleteItem`, `ConditionCheckItem` (`TransactWriteItems`*) | The table; `dynamodb:LeadingKeys` ∈ `IDENT#*`, `USAGEKEY#*`, `PENDING#*`, `GROUPMAP#*`, `VIS#*`, `LOCALUSER#*`, `SSOEXPECT#*`, `SSOREF#*` (added 2026-11-14, password users), `SETUPLINK#*` (added 2026-11-14, R2b-2 setup links), `GOVERNANCE`, `ACCT#*` (never `SYSTEM`, which holds the collector's `SyncStatus`) |
| Audit | `PutItem` **only** | The table; `dynamodb:LeadingKeys` ∈ `AUDIT#*` — no `UpdateItem`/`DeleteItem`, so the log stays append-only |
| Audit log group | `logs:CreateLogStream`, `logs:PutLogEvents` | `/llm-usage-lens/<env>/audit` only |
| KMS | `kms:Decrypt`, `kms:GenerateDataKey` | The CMK |

\* `TransactWriteItems` is authorised per contained action; the conditions
above apply to each item. The **execution role** may read only the SSM
parameters named in the task definition's `secrets` (from LiteLLM unit L1,
also `/llm-usage-lens/<env>/litellm/service-key`), with `kms:Decrypt` on
the key that encrypts them (the CMK, conditioned on
`kms:ViaService = ssm.ap-southeast-2.amazonaws.com`), plus the ECR-pull and log-write grants ECS requires. Nothing else.

**Ownership:** RP creates the task role with what the existing dashboard
needs — the **Reads** statement and writes limited to `ACCT#*` (Phase 4.9
account CRUD) and `IDENT#*` (Phase 4R.1 writes the identity record and the
master-user lockout counter at `IDENT#{oid}` on sign-in; added 2026-11-11,
security review — without it every sign-in fails closed on a deployed task) —
so a deploy between RP and 4R.2 works. Phase 4R.2 adds the remaining
access-control leading keys, the **Audit** statement and their assertions.
LiteLLM unit **L1** adds `LITELLM#*` to the write leading keys (moved from L2, 2026-11-14: L1 stores the connection at `LITELLM#CONFIG`); the task role
never gets SSM access ([LiteLLM spec](2026-11-10-litellm.md) — *Cloud
permissions*).

## Operations

- **Alarms:** running task count below desired (`ECS/ContainerInsights`
  `RunningTaskCount`); task restarts or failures (v1 signal:
  `PendingTaskCount` ≥ 1 for 5 minutes — a proxy; an ECS task-state-change
  rule would be an amendment adding an EventBridge rule);
  target-group unhealthy hosts and 5xx (**create mode only**); application
  5xx via a log metric filter; security events (in-app global-role grants,
  master-user sign-ins, failures and lockouts, and denied write attempts —
  Access Control — *Audit log*, D17) via a metric filter on the audit log
  group. Actions go to the existing SNS topic. Log contracts the
  filters read: the application 5xx filter needs a structured request log
  line (`$.status`), which no unit emits yet (gap, recorded in RP); the
  security filter keys on the audit record field 4R.2 defines:
  `$.category = "security"` (confirmed by 4R.2, 2026-11-12). An audit line
  that cannot be delivered to CloudWatch writes one stdout line
  `{"event":"audit.delivery_failed","requestId":…}` to the application log
  group; a metric filter (`AuditDeliveryFailures`) and alarm
  (`AuditDeliveryAlarm`) on it go to the same topic. The task receives the
  group's name as `AUDIT_LOG_GROUP_NAME`.
- **Runbook:** `docs/guides/operations.md` (created in RP) — alarms, first
  look at each, redeploy, secret and service-key rotation, master-user
  custody.
- **Cost posture:** Fargate tasks, ECR storage, CloudWatch Logs,
  Container Insights metrics (paid; the running-task alarm needs them), and
  the internal ALB only in create mode. No NAT, endpoint, cache, WAF or
  certificate cost.

## IaC layout

One CDK app in `infra/` with the three stacks; each deployable on its own
with a deploy and undeploy runbook. Stacks share values through **SSM
parameters, never CloudFormation exports** (an export locks the producer).
Deploy order: FoundationStack → DashboardServiceStack (→ CollectorStack in Phase 6). The **CI
deploy role** (GitHub OIDC) can push the ECR image, update the ECS service
and run CloudFormation for the DashboardServiceStack; it cannot read secrets. Its OIDC
trust is scoped to `repo:<githubRepository>:environment:<env>` (GitHub
environments `dev`/`prod`, with protection on `prod`), and CI runs
`cdk deploy <DashboardServiceStack> --exclusively`, never the FoundationStack. Because the
CDK deploy path assumes the bootstrap roles, "cannot read secrets" holds
only when the account is bootstrapped with a **scoped
`--cloudformation-execution-policies`** (not `AdministratorAccess`) — a
user action in the deployment guide; until then it is an accepted residual
risk (decided 2026-11-10, RP review).

**Verification (RP):** `cdk synth` plus assertions for both ALB modes —
import mode creates no ALB or listener; create mode creates exactly one
internal ALB with HTTPS only — the execution role (its `kms:Decrypt` carries the `kms:ViaService`
condition), the RP task-role statements (Reads, `ACCT#*` and `IDENT#*`
writes), and the absence of every "not created" resource. The
access-control statements and the audit `PutItem`-only statement are
asserted in Phase 4R.2.
Runs never run `cdk deploy` or call AWS.
