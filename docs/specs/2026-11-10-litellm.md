# LiteLLM Spec — Team & User Administration and LiteLLM-Reported Cost

**Status:** L0 (spec unit), 2026-11-10. Units L1–L8 build it (Implementation
Phases — *LiteLLM units*). Depends on the [Access Control spec](2026-11-10-access-control.md)
(roles, scopes, membership, audit, enforcement) and the
[Platform spec](2026-11-10-platform.md) (DashboardServiceStack, execution role, task role).

## Overview

The dashboard administers an **existing** LiteLLM proxy, limited to teams,
team members, users, keys, budgets, rate limits and spend reads, and shows
LiteLLM-reported cost per team and per user. The browser never talks to
LiteLLM: server code under `apps/dashboard/lib/litellm/**` calls a fixed
allowlist of operations with a **scoped service key** (never the master key),
after the Access Control policy module has authorised the caller on the target
dashboard team.

Out of scope, for every role (**hard limits**): model writes (`/model/*`
writes, team BYOK onboarding, `/team/model/add|delete`), global config
(`/config/*`, UI settings, guardrails, callbacks, SSO, alerting),
`/organization/*`, `/v1/agents*`, global resets and deletes
(`/global/spend/reset`), granting `proxy_admin`/`proxy_admin_viewer`, keys with
`permissions`, `allowed_routes`, a `key` value or no owner, bulk endpoints
(`/key/bulk_update`, `/team/bulk_member_add`, `/user/bulk_update`,
`/team/key/bulk_update`, `/team/permissions_bulk_update`), and any generic
passthrough route. Deploying or operating LiteLLM is never done here.

### Schema findings

- **Key values are returned only by generate and regenerate.**
  `GenerateKeyResponse.key` (required) is the plaintext; it also carries
  `token` (the hash). `/key/list` items are `UserAPIKeyAuth`/token rows with
  the hashed `token`, the masked `key_name` and `key_alias`; `/key/info`
  returns `info` "minus the hashed token" and **echoes back the `key` query
  value as passed** — so the gateway always passes the hash, and never calls
  `/key/info` without `key` (that would echo the service key itself).
- **`/user/new` creates and returns a key by default** (`auto_create_key`
  default `true`). The gateway always sends `auto_create_key: false` and
  `send_invite_email: false`.
- **`/key/generate` accepts a client-chosen `key`**, `permissions`,
  `allowed_routes`, `key_type` and `tags` (`tags` is Enterprise-only). None is
  ever sent; spend tags go in `metadata`.
- **Member role.** `Member.role` ∈ `admin`, `user`; a LiteLLM team `admin`
  can manage team settings directly, so the gateway always sends `user`.
- **User role.** `user_role` ∈ `proxy_admin`, `proxy_admin_viewer`,
  `internal_user`, `internal_user_viewer`. Members are created as
  `internal_user` (least privilege that can still use a key).
- **No member-level block** exists in `TeamMemberUpdateRequest`; `/user/update`
  has `blocked`, but it is proxy-wide (decision LD2). From RS2 (2026-11-19) the
  gateway sends `/user/update` for `resetUserSpend` only, with the body
  `{ user_id, spend: 0 }`, never `blocked`.
- **Response parsing.** `/team/info`, `/key/info`, `/models` and the spend
  logs declare untyped (`{}` or `additionalProperties`) responses. Their Zod
  schemas (L2) model only the fields the dashboard reads, drawn from the
  typed component schemas (`LiteLLM_TeamTable`, `LiteLLM_TeamMembership`,
  `LiteLLM_VerificationToken`, `SpendAnalyticsPaginatedResponse`,
  `LiteLLM_SpendLogs`), and strip everything else before use. A response
  missing a required field is `LITELLM_UNAVAILABLE` (a contract drift), never
  a partial render.
- **Rate-limit fields** (confirmed): team `rpm_limit`, `tpm_limit`,
  `model_rpm_limit`, `model_tpm_limit`, `team_member_rpm_limit`,
  `team_member_tpm_limit` on `/team/new` and `/team/update`; member
  `rpm_limit`, `tpm_limit` on `/team/member_update`; key `rpm_limit`,
  `tpm_limit`, `max_parallel_requests` on `/key/generate` and `/key/update`.
  All are nullable integers (or per-model maps); "unset" is **omitted**,
  never `0`.

## Roles and rights

Role words: **Viewer** = `internal-viewer` and members; **Lead** =
`internal-team-admin` within its team or department scope, and
`internal-org-admin` on every team (no configuration except the toggles and team links, LD24); **Auditor** =
`internal-auditor`; **Admin** = `internal-admin` (Access Control —
*Roles*).

| Role | Sees | Does |
|---|---|---|
| Viewer | Through their `litellmUserId` link (empty state if unlinked): own LiteLLM spend, budget, limits and own keys' metadata — **never key values** | Nothing (L7 adds key *requests*) |
| Lead | In scope: team spend and budget; members' spend, budgets and limits; keys' metadata; team model access | The Lead rows of the allowlist below |
| Auditor | Every LiteLLM read view, organisation-wide, read-only; never key values | Nothing — every LiteLLM write route returns `403` |
| Admin | Everything, every team | Every allowlisted operation, plus links, team creation, connection, toggles, gateway configuration |

Configuration (team links, LiteLLM team creation, the connection, toggles,
the gateway configuration) is `internal-admin` only, with one exception
(LD24, user, 2026-11-16): `internal-org-admin` may also write the operation
toggles (including reset) and the team links. The connection (URL and
connection test), team creation and the gateway configuration stay
`internal-admin` only; an org-admin calling them gets `403`. *Amended
2026-11-17 (user, management improvements D16):* `internal-org-admin` may
also create, approve and remove **LiteLLM user links** (never its own) and,
on OSS and only when SSO is not enabled (user, 2026-11-18, unit LW1), **create a LiteLLM user and link it** (`createUser`); the usage
identities and aliases stay `internal-admin` (Access Control — *LiteLLM
user links*). Team links and the user list moved from Settings to
Management → LiteLLM with unchanged permissions (D3, D4, agent
decisions).

**App teams (2026-11-17, user; L4b).** The dashboard's teams (app teams) are
managed separately from LiteLLM teams. A **Lead sees the spend of its app
team** — the LiteLLM team figure when the team is linked, otherwise the
**sum of its members' LiteLLM spend** — and **Admin, org-admin and Auditor
see both the LiteLLM team and the app team** (the member sum as a second
figure on a linked team, on request). Who may set a link is unchanged (LD24,
LD30). (App Teams spec — *Spend source*, *Decisions*, L4b)

## Allowlist (the gateway)

`lib/litellm/` exposes **one typed function per row**, with a fixed method and
path. Its strict Zod input schema **builds** the LiteLLM body from typed,
server-resolved values (never a forwarded client body; unknown fields are
rejected), and every response is Zod-parsed. Anything not in this table
cannot be called. A structural test (L2) enumerates the gateway and fails when
the set differs from this table.

**Resolution.** Route paths carry the dashboard `teamId` and member `oid`,
never LiteLLM ids. The server resolves `litellmTeamId` from the team link and
`litellmUserId` from the identity link; a key's `token` (from a list the
caller is allowed to see) is accepted only after `/key/info` confirms its
`team_id` equals the linked team — otherwise `404` with no write.

**Privileged targets are refused.** Before `addTeamMember`,
`generateMemberKey`, `updateMemberKey`, `rotateKey` and `revealKeyRequest`,
the server reads the target with `getUser` and refuses — `409
PRIVILEGED_TARGET`, with no LiteLLM write — when its `user_role` is not
`internal_user` or `internal_user_viewer`, or when it is the service user.
A key inherits its owner's proxy role and these keys carry no
`allowed_routes`, so a key for a `proxy_admin` or `proxy_admin_viewer` user
would reach the hard-limit routes (LT18). Such people are managed by the
LiteLLM operators directly.

### Service key `allowed_routes`

The service key's `allowed_routes` are the paths below, nothing else. A
test (L2) asserts this list, the runbook's list and the gateway's set of
paths are equal; the two temporary wildcards are compared as written.

**Temporary wildcards (amended 2026-11-15, user; LD4).** LiteLLM 1.109.1
(OSS, tested live 2026-11-15) matches an `allowed_routes` entry only
exactly, as a prefix (`entry + "/"`), as a route group, or with a trailing
`*`; a `{team_id}` or `{key}` template never matches and a mid-path `*` is
not supported. The three templated routes are therefore reachable only
through **`/team/*` and `/key/*`**, which the key carries **temporarily** in

(future-improvements — *Exact templated `allowed_routes`*). The wildcards
also admit hard-limit routes (`/team/delete`, `/team/model/add`,
`/key/bulk_update`, …), so the dashboard itself is the guardrail
(*Gateway guardrails* below).

**No inference with the service key (amended 2026-11-15, user; LD18).**
Because an entry also matches as a prefix, `/models` admits
`/models/{model}:generateContent`, and a key with no `models` may call every
model: the live test passed an inference call through the route gate. The
service key must not be able to call any model. L2 verifies on the
company's LiteLLM which key setting refuses inference while `GET /models`
still lists names (candidates: a `models` restriction such as
`no-default-models`, `max_budget: 0`, `rpm_limit: 0`), records it in the
runbook's key-creation step, and the runbook's verification proves that a
model call with the service key is refused. If no setting keeps `/models`
working, the model list moves to another read route by a spec amendment.
The other prefix matches (the daily-activity routes, `/audit/{id}`) are
read-only and covered by the gateway guardrails.

### Gateway guardrails (decided 2026-11-15, user)

While the key carries `/team/*` and `/key/*`, LiteLLM no longer stops a
hard-limit call, so the dashboard must never send one:

1. **One outbound choke point.** Every LiteLLM request goes through one
   function in `lib/litellm/` that checks the method and the route template
   against the allowlist table above and refuses anything else before any
   network call (`LiteLLMRouteNotAllowed`, recorded on the span, never
   sent). No generic passthrough, no caller-supplied path.
2. **Path parameters are validated, then encoded.** `{team_id}`, `{user_id}`
   and `{key}` match strict patterns (no `/`, `..`, `?`, `#` or `%`) and are
   `encodeURIComponent`-encoded, so a parameter cannot reach another route.
3. **Hard-limit denylist test.** A test sends every hard-limit route in
   *Scope* (including `/team/delete`, `/team/block`, `/team/model/add`,
   `/team/model/delete`, `/key/bulk_update`, `/team/key/bulk_update`,
   `/team/bulk_member_add`, `/team/permissions_bulk_update`,
   `/user/bulk_update`, `/key/regenerate` without a token, `/key/service-account/generate`)
   through the choke point and expects refusal with no request reaching the
   fake LiteLLM.
4. **Exact bodies.** Builders emit only the fields listed per operation
   (LT4); a body never carries `allowed_routes`, `permissions`, `user_role`,
   `key`, `models` widening or `key_type`.
5. **Toggles and audit.** Read and write operations stay behind their
   operation toggles (defaults per LD10; reads default on, LD19) and the dashboard audit log (*Audit*).
6. **Visible exception.** The connection test reports
   "service key uses temporary wildcards (`/team/*`, `/key/*`)" as a warning
   on the Settings → LiteLLM panel while either wildcard is present, and
   the runbook says why and when to remove them.

## Security architecture

1. **Backend-for-frontend.** Only `lib/litellm/**` (`import "server-only"`)
   and Route Handlers call LiteLLM; Client Components fetch same-origin Route
   Handlers (Rule 10).
2. **Authorization before every call** (Access Control — *Enforcement*):
   session → `resolveScope`/`can` on the dashboard team → toggle → edition →
   input validation → id resolution → LiteLLM. A key or user outside the
   caller's linked, in-scope teams returns the same `404` body as a missing
   one.
3. **Service key, never the master key.** A dedicated LiteLLM user
   (`svc-llm-usage-lens`, `user_role: proxy_admin`, decision LD3) owns one
   key with the `allowed_routes` above, a `key_alias` and no `models`. The
   operators create it with the master key, which never enters the dashboard,
   its CDK, CI or SSM parameters.
4. **Storage and loading.** SSM `SecureString`
   `/llm-usage-lens/<env>/litellm/service-key`, created and updated **by
   hand**, encrypted with the **project CMK** (decision LD6). The DashboardServiceStack
   task definition declares `LITELLM_SERVICE_KEY` under `secrets`
   (`valueFrom` the parameter ARN); the **execution role** reads it at task
   start. Application code never calls SSM; the value is never in
   `environment`, CDK context, outputs or the image. Standard parameter: no
   cost; KMS usage is covered by the existing CMK.
5. **It never leaks** — not in the repo, `.env.example` values, the client
   bundle, the UI, API responses, logs, OpenTelemetry attributes, error
   messages, DynamoDB items or the audit log (Rules 50.6, 50.9). `env.ts`
   validates it server-only (never `NEXT_PUBLIC_*`); it is read at request
   time. When missing, LiteLLM features report "not configured" and the rest
   of the dashboard runs.
6. **No UI for the key.** Admins see only "service key configured: yes/no"
   and the connection test result: `ok`, `unauthorised` (LiteLLM `401` —
   "service key rejected — rotate and redeploy", never retried with another
   key), `routes out of date` (`403` on an allowlisted route) or
   `unreachable`.
7. **The connection.** The base URL is Admin-set in Settings, stored in
   DynamoDB, versioned and audited, and must match `LITELLM_ALLOWED_HOSTS`
   (deploy-time, `env.ts`; host or `host:port`), be `https` when
   `APP_ENV=prod`, and carry no userinfo, query or fragment (`400`
   otherwise, nothing called). A new URL is saved only after a successful
   connection test against it. Timeouts 10 s; GETs retried at most twice with
   backoff; writes never retried. *Added 2026-11-24 (unit ST1, D-ST4):* the
   optional `LLM_LENS_LITELLM_BASE_URL` (`env.ts`, default
   `http://localhost:4000`) is the value the Settings form **offers** when no
   connection is saved; it is never saved by itself and never bypasses
   `LITELLM_ALLOWED_HOSTS`.
8. **Failures** map to `{ error: { code, message } }` with sanitised messages;
   no upstream body is passed through. An outage shows "LiteLLM unavailable"
   on the LiteLLM sections only (Rule 40.4).
9. **Key values.** A generated value is returned once, in that response only
   (`Cache-Control: no-store`), shown once with a copy action, and never
   stored, logged or cached. Lists show the alias and the token id (LD27: under the Organisation cap
   the alias is dropped and the key shows as "…" plus the token id's last
   four characters; LiteLLM's masked `key_name` was specified but never
   built). Every call that identifies a key sends its
   **hash**.
10. **Rate limits are LiteLLM's.** The dashboard configures them through the
    gateway; it has no rate limiting of its own (Access Control —
    *Enforcement* item 6).
11. **Enforced access only.** While `AUTH_ACCESS_MODE=open`, every LiteLLM
    route returns `403` with no LiteLLM call (Access Control — *Rollout*).
12. **Writes** use the same-origin check, Zod validation, body/path id
    matching, `version` (`409`) on dashboard items and `403` before parsing;
    every LiteLLM write route is in `write-routes.integration.test.ts`.

  hostname, and the task security group's existing egress already allows it.
  On the LiteLLM side, its security group must accept the LiteLLM port

## Identity mapping and members

- **Team link:** dashboard `teamId` → LiteLLM `team_id`, one-to-one in v1
  (both directions unique), Admin-managed and audited. Department-scope Leads
  act on each linked team in their department. **Superseded 2026-11-17
  (user; App Teams spec, L4b):** "Unlinked teams show 'not connected to
  LiteLLM'" — an unlinked app team now shows its member-sum spend and one
  line saying its budgets, limits and keys are managed in LiteLLM; the
  absence of a link is the flag (no new entity or key), and the link itself is
  unchanged. Reason: LiteLLM limits how many teams can exist, so several app
  teams share one LiteLLM team and need spend without a team of their own.
- **App teams and LiteLLM teams are separate (2026-11-17, L4b).** An app
  team (`teamId`, membership = the Access Control affiliation, at most one
  per person) and a LiteLLM team (`team_id`) are different concepts; UI copy
  says "team" only for an app team and "LiteLLM team" for the proxy's. App
  membership and LiteLLM membership stay separate writes. For an unlinked
  team the **member sum** resolves each member's LiteLLM user from
  `IdentityLink.litellmUserId`, else `findUserByEmail` on the verified email
  (LD13 pattern, nothing written). An unmatched member is "not in LiteLLM",
  never $0 (App Teams spec — *Member sum*).
- **User link** (`IdentityLink.litellmUserId`, Access Control —
  *Identity links*):
  - **OSS (`dev`):** `user_id` = `user_email` = lower-cased work email; the
    dashboard creates the user when missing (`addTeamMember`).
  - **Enterprise (`prod`):** LiteLLM creates users at SSO sign-in; the link
    is the `user_id` LiteLLM assigned, found by `findUserByEmail`. The
    dashboard **never creates** a user on Enterprise; a person not yet signed
    in to LiteLLM gets "sign in to LiteLLM once, then retry" (`409
    CONFLICT`). **Confirmed by the user 2026-11-10:** on the company's
    Enterprise deployment the SSO-assigned `user_id` is the **email**. The
    dashboard still resolves it with `findUserByEmail` and stores the
    `user_id` LiteLLM returns, never a value it composes itself, so a future
    change of LiteLLM's SSO mapping cannot create a mismatched link.
  - Changing edition re-resolves links (runbook step, audited).
  - **Linking (management improvements D16, user, 2026-11-17).** On
    Management → LiteLLM → *LiteLLM users*, Admin and org-admin link an app
    user to a LiteLLM user: a **match** (same verified email) after an
    approval click; a **manual** link to a LiteLLM user found by search,
    with a written reason; or, on OSS only and only when SSO is not enabled (user, 2026-11-18, LW1), **create and link**
    (`createUser`). Never automatic (Access Control D27), never on oneself,
    one-to-one, privileged targets refused (Access Control — *LiteLLM user
    links*).
- **Members:** Leads add only people who are already dashboard members of
  that team. Removing a dashboard membership never changes LiteLLM: the UI
  says the person is still in the LiteLLM team and offers "also remove from
  LiteLLM" (`removeTeamMember`, separate and audited). Settings lists such
  orphaned LiteLLM members. *Superseded 2026-11-17 (management improvements
  D16a): Management → LiteLLM → *LiteLLM users* lists them under **Members
  of one team** for a linked team; Settings has no orphans list.*
- **Enable/disable** blocks or unblocks every key the member owns in that
  team; it never deletes keys or data (decision LD2).

## Budgets and limits

- Team `max_budget`/`budget_duration`/`soft_budget`: Admin sets; a Lead may
  only lower `max_budget` and `soft_budget`.
- Member `max_budget_in_team` ≤ team `max_budget`; reset spend and reset
  budget act on exactly one member of one team.
- UI note on team keys: "Only the team and team-member budgets are enforced
  on team keys; the owner's personal budget does not apply" (LiteLLM docs).
- Limits are positive integers or **unset** (omitted; never `0`, which
  LiteLLM may read as "block"). The server reads the team's current limits
  first: a member or key limit above the team's (or a key limit above the
  member's) returns `400` with no LiteLLM call. Per-model limits only for
  models the team already has. A Lead may only lower team limits.
- A Lead raising team values gets `400 BAD_REQUEST` with no LiteLLM call.
- Not exposed (RS2, 2026-11-19: the user-level spend reset `resetUserSpend` is the one user-level write, body `{ user_id, spend: 0 }` only): user-level limits outside a team, `mcp_rpm_limit`,
  `tag_rpm_limit`, `tpd_limit`, `rpm_limit_type`/`tpm_limit_type`,
  `model_max_budget`, `temp_budget_*`.
- **Model access:** a team's `models` is a subset of `/models`; an unknown
  model returns `400`. No model write exists.

## Budget reset requests (unit M4; user, 2026-11-17)

*Added 2026-11-17 at the user's request (items 6–8 of
the management improvements run plan, removed on 2026-11-18 after its

as top priority"). Decisions MG-D8 to MG-D13 (with MG-D11a and MG-D12a) are

the [Data Model spec](2026-05-15-data-model.md) — *Budget reset entities
(unit M4)*; the permission rows and threat items BR1–BR10 are in the
[Access Control spec](2026-11-10-access-control.md).*

**Which reset an approved request runs (MG-D11; read from the contract, not
from memory).** `docs/litellm/openapi.json` is a single-line JSON file, so
the references are JSON paths, not line numbers:

- `paths["/team/{team_id}/member/{user_id}/reset_spend"].post.description`:
  "Reset a team member's tracked spend against their per-member budget. … this
  is the only endpoint that does. The cross-pod spend counter and cached
  membership reads are invalidated so the reset takes effect on the member's
  next request …". Body `components.schemas.ResetSpendRequest` (`reset_to`,
  required); the dashboard sends `0` (`lib/litellm/operations.ts`,
  `resetMemberSpend`).
- `paths["/team/{team_id}/member/{user_id}/reset_budget"].post.description`:
  "Put a team member back on the team's shared default member budget … Spend
  is untouched." Response `components.schemas.TeamMemberResetBudgetResponse`
  (`budget_id`, `previous_budget_id`, `budget_source`).

A member is blocked by their per-member budget when their tracked membership
spend reaches `max_budget_in_team`. `reset_budget` leaves that spend as it
is, so the member stays blocked unless the team default happens to be
higher; `reset_spend` clears it, effective on the next request. **An approved
request therefore runs `resetMemberSpend`**, the L4 operation, unchanged and
called through `lib/litellm/operations.ts` (no `lib/litellm/**` edit in
slice A). The fake LiteLLM records the call (`test/fakes/fake-litellm.ts`
allowlists the `reset_spend` path); the slice A test asserts that an
approval sends exactly one `POST /team/{team_id}/member/{user_id}/reset_spend`
with `{ "reset_to": 0 }` and no `reset_budget` call.

**Consequence for the defaults.** `resetMemberSpend` stays default **off**
(LD10; a default that is off today is not weakened). The request control is
shown only while **both** `requestBudgetReset` and `resetMemberSpend` are
enabled ("hidden, never dead"), so on a fresh deployment the button is absent
until an Admin or org-admin switches `resetMemberSpend` on (Settings →
LiteLLM → Guardrails). That switch is a user action, listed in the run
report.

**Flow (slice A).**

1. **Request.** On *My usage*, a member of a linked team sees "Request a
   budget reset" beside "Request a budget increase" (the `mailto:` link
   stays). An optional reason: plain text, at most 280 characters, rendered
   as text only. One open request per person per team (a second is
   `409 CONFLICT`); an open request expires after 7 days (L7's precedent).
   No LiteLLM call.
2. **Notification.** Each lead whose scope covers the team (a team-scope
   `internal-team-admin` of the team, or a department-scope one of its
   department), except the requester, gets an in-app notification; when
   there is none, every `internal-org-admin` and `internal-admin` holder
   (stored grant or last-seen role, the `leadEmail` precedent), except the
   requester.
3. **Decision.** From the bell or from the open-requests list on the Team
   page's Budgets view, a decider approves (an `AlertDialog` naming the
   person and the effect: "Reset <name>'s spend in <team> to $0. They can
   spend again at once.") or denies. The server re-reads the request and
   re-checks scope, membership, link and both toggles **at the decision**,
   never at the request.
4. **Reset.** Approve moves the request `open → approving` with a conditional
   write (two approvers cause one reset; the second gets `409 CONFLICT`),
   reads the member's spend and budget from `getTeam`, calls
   `resetMemberSpend`, then in one transaction writes the `BudgetReset` ledger
   item (`trigger: "request"`), moves the request `approving → approved`,
   deletes the open-request claim and writes the audit records
   (`litellm.member.reset-spend` and `budgetreset.request.approve`). If the
   LiteLLM call fails, the request returns `approving → open`, the reset is
   audited `failed`, and nobody is notified (MG-D12a).
5. **Result.** The requester is notified on approved, denied and expired.

**Slice B (counts).** It waited for L6 on `main`, because `lib/litellm/**`
was L6's until it landed. The direct reset routes and the bulk reset write the

route-less dashboard operation (MG-D11a); the scoped count read feeds *My
usage*, the Team page's Budgets view and the Organisation tab (MG-D10).

## Cost visualisation and provenance

- **Sources:** team spend from `getTeam` and `getTeamDailySpend`; user spend
  from `getUser` and `getUserDailySpend`; request detail from
  `listSpendLogs`; Enterprise organisation view from `getGlobalSpendReport`
  (server-side, filtered to scope). `get_spend_routes` keys are never created.
- **Spend source per app team (2026-11-17, L4b).** A linked team's headline
  is `getTeam` and `getTeamDailySpend` (`spendSource: "litellm-team"`); an
  unlinked team's is the **member sum** — `getUserDailySpend` per member,
  `timezone=0`, rows added per UTC day (`spendSource: "member-sum"`), computed
  in `lib/litellm/member-sum.ts` with `{ members, matched, unmatched, pending }`
  coverage always returned. Bounds: 5 concurrent reads, 200 members per team
  (`422 TOO_MANY_MEMBERS`, no LiteLLM call), 200 LiteLLM calls (member
  reads, email lookups and per-team daily reads) per Organisation request;
  membership is read once per team, so a team that crosses 200 members
  between reads is an `open-team` row there, never a `422`; any failed
  member read fails the request, no partial sum (LD34, LD35). Every "Spend"
  figure on the Organisation and Team pages covers the selected date range;
  `team_info.spend` shows only beside the budget as "Spent this budget
  period" (LD36). Wherever both figures appear the UI explains why they differ (the
  LiteLLM team figure includes keys owned by nobody in the app team; the
  member sum includes each member's spend in any LiteLLM team and on personal
  keys). The Organisation cap hides per-member `spend` but the team's member
  sum is always shown (LD31). Both figures are LiteLLM-reported. (App Teams
  spec — *Spend source*, L4b)
- **Provenance (Rule 20.3):** LiteLLM spend is LiteLLM's own price
  calculation, not billed cost — labelled **"LiteLLM-reported"** wherever it
  appears alone. Combined totals follow shared contract §5 as specified in
  *Combined usage and My usage (L6)* (direct Bedrock excluding gateway
  principals + LiteLLM-reported; the gateway slice as "billed via LiteLLM";
  a reconciliation row; parts always shown; while no gateway is configured,
  hidden from Viewers and Leads with a warning to the global readers —
  Admin, org-admin, Auditor, LD38). The organisation's LiteLLM part covers
  LiteLLM teams only; the user declined the proxy-wide read (U1, 2026-11-17) — built in L6.
- **No server-side fetch of `/api/*`:** LiteLLM views read their routes only from the browser; a client component that renders during SSR must not run a relative `fetch` (it cannot resolve on the server). Server Components that need LiteLLM data read it through `lib/litellm/**` directly (agent decision, 2026-11-17: CI logged "Failed to parse URL from /api/litellm/me").
- **Caching:** responses send `Cache-Control: private, no-store`. TanStack
  Query holds LiteLLM data for 60 seconds (`staleTime`, PERF-2); after a
  write the UI shows the write response, then refetches. USD only; LiteLLM
  dates are UTC and labelled.
  **Server read cache (user, 2026-11-17, Phase 5 *Performance and caching*,
  unit PERF-3; until it is built, LiteLLM reads are not cached on the
  server).** `lib/litellm/read-cache.ts` keeps, per task and in memory only,
  the raw upstream body of these reads, keyed by method, route template,
  parameters and query: `listProxyModels` and a positive `findUserByEmail`
  match for 5 minutes; `getTeam`, `listProxyTeams`, `getTeamDailySpend`,
  `getUserDailySpend` and `getGlobalSpendReport` for 60 seconds. The entry
  is scope-independent: authorization, scope filtering, toggles and the
  audited views run after the read, on every request (Access Control —
  *Enforcement* item 4). **Never cached:** `getKey`, `listKeys`, `getUser`,
  `searchUsers`, `listSpendLogs`, `listProxyAuditLog`, any error or outage,
  any key value, and every LiteLLM read a write path makes (the budget,
  limit, subset and privileged-target checks stay live — LT13, LT14,
  LT18). The one cached read a write path may use is not a LiteLLM read:
  the dashboard's own account list (`getAllAccountsCached`), which is not
  authorization data (Data Model — *Access Patterns*, with its accepted
  residual risk). A
  successful write evicts the entries of its team and user (`resetUserSpend` evicts the user's entries across all of their teams, RS2); a request that
  carries `Cache-Control: no-cache` (the refetch after a write and the
  top-bar refresh, Design System — *Caching Strategy*) bypasses the cache
  and replaces the entry, at most once per 10 seconds per key and task
  (Design System — *Caching Strategy*, minimum refresh interval). The cache
  is capped at 500 entries and 32 MB, least recently used first (same
  section). A structural test pins the cached list, so a new
  operation is uncached unless the spec adds it. Residual risk, accepted
  with the decision: a spend, budget or model list shown by the other task
  can be up to its TTL old; nothing is enforced from a cached value.
  **In-flight sharing (PERF-1):** identical concurrent `GET`s share one
  upstream call only when they are read-path calls of an operation on the
  cached list above; nothing is kept after the call settles. A write path
  never joins an in-flight read, and the never-cached operations (`getKey`,
  `listKeys`, `getUser`, `searchUsers`, `listSpendLogs`,
  `listProxyAuditLog`) are never shared: each caller makes its own call, so
  a check never acts on a response that was requested before it (LT13,
  LT14, LT18).

Authority: shared contract §5; this spec's Allowlist, Provenance, Data model additions, LD10, LD19, LD20, LD23, LD24, LD27, LD33–LD37; Access Control — Navigation and landing by role, Organisation cap, Enforcement; Data Model — DailyRollup, byUser keys, Non-Model Charges; Rules 10, 20.1, 20.3, 20.8, 60.10, 60.24a.*

**Scope.** The gateway configuration and its route; one pure module that computes every combined figure; read routes that return them; the UI on Overview, Teams, Team Detail, Management → Users (user detail) and My usage; the Settings → LiteLLM *Gateway* sub-tab. The Bedrock routes (`/api/overview`, `/api/teams`, `/api/teams/[id]`, `/api/users`, `/api/me/usage`) are **unchanged**: combined figures come from their own routes and sections, so a LiteLLM outage never breaks a Bedrock page and the rollup cache keeps working (L3 outage rule; Rule 60.10). (Teams panel replaced by M5, 2026-11-18.)

### Gateway configuration

- **Entity** `GatewayConfig` at `LITELLM#CONFIG` / `GATEWAY`; in code `BedrockGatewayConfig`, because `LiteLLMGatewayConfig` already names the `config.yaml` operations branch (LD19).
- **Schema** (`packages/shared`, strict): `principals: { type: "iam-role" | "usage-key", value }[]` (≤ 20), `accountIds: AccountId[]` (12 digits, ≤ 10), `version` (int ≥ 1), `updatedAt`, `updatedBy`.
- **Validation** (`400`, no audit record): `iam-role` trimmed, `^[\w+=,.@-]{1,64}$`, compared case-insensitively; `usage-key` trimmed, 1–512 characters, no control characters; a value whose canonical usage identity is a **person** (an email) is refused in both types, because excluding a person's key would hide real usage (LT29); duplicates after normalisation refused (principals and account ids alike); every account id must exist in `AccountMeta`. Both lists empty is allowed and means "clear".
- **Matching** (exact only, no substring or wildcard): a `usage-key` matches the byUser key equal to it; an `iam-role` R matches a byUser key equal to R, `arn:aws:sts::<12d>:assumed-role/R/<session>` or `arn:aws:iam::<12d>:role/[path/]R`. The `AROA…:<session>` principalId form carries no role name; the Admin enters it as a `usage-key` (runbook §8).
- **Configured** = at least one principal or account id (agent decision, 2026-11-17: either one is enough to remove LiteLLM's Bedrock traffic from the direct figure, so either ends the double count), returned as `gatewayConfigured` (distinct from LD37's `configured`, which is the LiteLLM connection).
- **Route** `GET, PUT /api/litellm/gateway`: GET Admin, org-admin (LD24: reads add org-admin), Auditor; PUT Admin only, `403` and one `denied` record for anyone else (LT30). PUT body `{ version: number | null, principals, accountIds }`; a stale version → `409 CONFLICT`. Each successful write appends one audit record `litellm.gateway.update` (target `litellm-gateway/default`, the lists before and after; nothing secret) in the same transaction. No stored item → `200 { gatewayConfigured: false, version: 0, principals: [], accountIds: [] }`.
- **Read per request, never cached:** it decides what Viewers and Leads see, so a stale copy would show double-counted totals (LT33); shared contract §7 lists Settings data as read per request. One `GetItem` per combined request.
- **No toggle:** `setGatewayConfig` is a dashboard-only configuration write (*Writes*).

### LiteLLM reads used

No new allowlisted operation (agent decision, 2026-11-17: a proxy-wide `/user/daily/activity` read without `user_id` would widen the allowlist, and widening a security control is the user's decision — implementation-phases *Decision policy*; listed under *User decisions* below).
- **Organisation:** the LD33 LiteLLM-teams total over the range from `getTeamDailySpend` (`/team/daily/activity/aggregated` with the listed teams), with its `breakdown.providers` for the provider split and the reconciliation. Spend on keys outside any LiteLLM team is not in it; the UI says so ("LiteLLM teams only").
- **Team:** `getTeamDailySpend` for the linked LiteLLM team (LD36).
- **Person:** `getUserDailySpend`. Every page counts as one LiteLLM call against the LD34 budget of 200 calls per request; a row that does not fit degrades as LD34 describes, never as a partial sum (L6 review, 2026-11-17). **Paging fix:** the contract pages `/user/daily/activity` (`page`, `page_size` ≤ 1000, default 50, `metadata.has_more`); the builder sent neither, so a long range could be truncated. L6 sends `page_size=1000` and loops while `has_more`, at most 10 pages; beyond that the read returns `503 LITELLM_UNAVAILABLE`, never a partial sum (LT34; LD35 precedent). `/team/daily/activity/aggregated` has no paging and is unchanged.

### The computation (`lib/litellm/combined.ts`, server-only, pure)

Inputs: the dated rollups R for `[dateFrom, dateTo]`, the gateway config (account set A, matcher G) and the parsed LiteLLM daily rows; no I/O (a loader, `combined-data.ts`, reads and calls it).
- `slice(r)` = `r.cost` when `r.accountId ∈ A`, else `Σ_m Σ_{k: G(k)} r.models[m].byUser[k].cost`; `direct(r) = r.cost − slice(r)` (below −1e-6 is an invariant defect, `500`; within tolerance clamped to 0).
- **Organisation:** `bedrockExact = Σ r.cost` (with `nonModel`), `gatewaySlice = Σ slice(r)`, `bedrockDirect = bedrockExact − gatewaySlice`, `litellm` = the teams total (all providers), `combined = bedrockDirect + litellm`; `byProvider[]` from the LiteLLM breakdown (non-Bedrock providers appear only there, labelled by provider).
- **Reconciliation:** `litellmBedrock = Σ breakdown.providers[p].spend` for `p ∈ BEDROCK_PROVIDERS = ["bedrock"]` (a tested constant), `difference = gatewaySlice − litellmBedrock`, `differencePct = difference / gatewaySlice` (null when the slice is 0). Always shown, never thresholded away.
- **Team T (linked):** `bedrockDirect = Σ_{r: r.teamId = T} direct(r)`, `litellm` = the linked team's spend, `combined = bedrockDirect + litellm`. An unlinked team has `combined: null, reason: "not-linked"`; a team whose account is a gateway account has `bedrockDirect = 0` and its slice shown.
- **Person P** (key set K: the caller's own usage keys; for another person the canonical email of the LiteLLM user's `user_email` plus that identity's usage identities and aliases): `bedrockDirect = Σ_{r: r.accountId ∉ A} Σ_m Σ_{k ∈ K, ¬G(k)} byUser[k].cost` (model cost only), `litellm` = the paged `getUserDailySpend` total (0 with `litellmUser: false` when there is none), `combined = bedrockDirect + litellm`.
- **Estimates:** a person's figure always has `costEstimated: true` (§5); organisation and team figures have it when a principal split took part or any rollup in R is unfinalised; `provisional: true` when any rollup in R has `costFinalized: false`.
- **Dates:** the same inclusive UTC days on both sides (`start_date = dateFrom`, `end_date = dateTo`, `timezone=0`; Rule 20.1, LD20), capped at 90 days (Rule 20.8).
- **Rounding:** sums unrounded; the response rounds each figure to 6 dp, `combined` from the unrounded parts; the UI shows 2 dp.
- **Visibility** `combinedVisibility(globalReader, gatewayConfigured)`: global readers (Admin, org-admin, Auditor) get `show` when configured, else `warn`; everyone else `show` when configured, else `hidden`. `hidden` is applied by the server: the response carries no `combined`, no slice and no reconciliation. org-admin gets the warning, not hiding (agent decision, 2026-11-17: it is a global reader of every Usage page; §5 names Admins and Auditors only — proposed amendment "global readers").

## Residual risks

- **App teams (L4b, 2026-11-17).** On a team of one or two members the member sum equals or nearly equals one person's cost, even under the Organisation cap (LD31, accepted by the user). Membership has no history: a mover's earlier spend follows them to the new team for any date range; a daily membership snapshot would fix it and needs a scheduler (`docs/future-improvements.md`). A large unlinked team costs one LiteLLM read per member on every view (bounded by LD34).
- Under the Organisation cap the keys read still returns each key's pseudonymous `tokenId` with its spend, while the `litellm.key.generate` and `litellm.key.update` audit records carry the same `tokenId` with the `litellmUserId` and `keyAlias`. A global reader (Admin or Auditor), who can read both, can join them and re-identify key spend. This held under LD23 already (not a regression from LD27); `tokenId` stays because every key write needs it. Recorded at the key-alias review (2026-11-17). **Accepted by the user, 2026-11-17** ("Accept risks"): the audit fields stay, since the Organisation cap keeps the audit log available (Access Control — *Organisation cap*) and only the audited global readers can join.
- A Lead viewing a member of its team in *Users* sees that person's total LiteLLM spend and daily spend, including spend in teams outside the Lead's scope: LiteLLM reports a user's spend across all teams and `/user/daily/activity` cannot be filtered by team on OSS (L3b; recorded for the user to accept or narrow).
- The service user is `proxy_admin`; its reach is bounded only by
  `allowed_routes` enforcement in LiteLLM (fixed since 1.83.14). A LiteLLM
  regression would widen it — mitigated by the version floor, the advisory
  check and rotation.
- `/team/update` and `/key/update` accept many fields; protection relies on
  the gateway's builders (tested), not on LiteLLM.
- LiteLLM spend is LiteLLM's price map; drift against billed Bedrock cost is
  surfaced (reconciliation), not corrected.
