For a **worker** session (`.claude/prompts/worker_prompt.md`). The coordinator
sends one unit at a time as a brief file. This plan holds the decisions,
the ownership and the tests of six units. The four other units of the same
plan (LW1, SYNC1, SYNC2, INV2) are in `docs/plans/litellm_user_sync.md`

commit, with the sentences under "Spec" below, and records every decision

overrides a rule.

   `http://localhost:3000`.

   teams, not every app team.

   section.

   instead of a dropdown of all users.

   options. The "Team admins — scope" and "Visibility scope" dropdowns go.
   "Pending and stale access" is about that team's invitations.
8. Manage → Users: the users table first, with the search inside the
   People section (as on the LiteLLM users page).
9. Manage → Users: a created-date column.
10. Manage → Users: sort by column, sorted by the API. The same in other
    tables where relevant.
11. Settings → Sync: a button to refresh on demand.
12. Settings → LiteLLM → connection: a green check and "LiteLLM connection

    `LLM_LENS_LITELLM_BASE_URL`.
13. Settings → Accounts, Add account: Account ID, Department ID and Team

    team and so on.
14. Manage → Audit, gateway source: it shows "LiteLLM unavailable".
15. Manage → LiteLLM → users: no linked account in the table row, only
    the buttons; the linked account is on the user's detail.
16. Manage → Users: clicking a user opens a page with all their
    information and the ways to edit it: name, email, linked accounts with
    unlink and reset, team and role.
17. Manage → Audit: the access-review export button near the top.

### LF1 — LiteLLM pages: fixes and clean-up

Items 2, 3 and 14 are defects: **reproduce each with a failing test before
changing code** (the response LiteLLM really sends, from
`docs/litellm/openapi.json` and the fake LiteLLM), then fix the cause.

- **D-LF1 (items 2, 3).** One schema per response, used on both ends
  (Rule 10.4): the route parses what it returns with the same exported
  schema the client parses. The all-users search and the list must not
  share a URL with two shapes; if they do today, give the search its own
  response schema and query key. A field LiteLLM may omit is optional or
  nullable in the gateway schema, never assumed. *Reason:* both errors are
  a client schema that does not match what the route returns.
- **D-LF2 (item 14).** On LiteLLM OSS the proxy audit log is an Enterprise
  endpoint. The gateway source then shows a named state, "The LiteLLM
  audit log needs LiteLLM Enterprise", not "LiteLLM unavailable". If the
  test shows another cause on Enterprise, fix that cause. "LiteLLM
  unavailable" stays for a real outage only.
- **D-LF3 (items 4, 5).** A "LiteLLM team" is a team that exists in
  LiteLLM (`listTeams`), whether or not it is linked. The team dropdown of
  "Members of one team" and the LiteLLM teams table list those only; app
  teams with no LiteLLM team are not shown there (App Teams spec — *the
  Organisation view's two tables* is the precedent).
- **D-LF4 (item 15).** The LiteLLM users table shows no linked-account
  column; the row keeps its buttons. The linked account is shown in the
  user's detail, with the link state.

**Owns:** `components/manage/users/LiteLLMUsersList.tsx`,
`LiteLLMLinkCell.tsx`, `components/litellm/UserSearch.tsx`,
`AuditSection.tsx`, `app/dashboard/manage/litellm/**`,
`app/api/litellm/users/route.ts` and `users/[litellmUserId]/route.ts`
(reads only), `app/api/litellm/audit/route.ts`, the LiteLLM teams table
component, the response schemas in `packages/shared/src/schemas/user-links.ts`,
their tests, `e2e/manage-users-links.spec.ts`, `e2e/litellm-*.spec.ts`.

| Test | Proves |
|---|---|
| T-LF1 | Item 2: a LiteLLM user with no usage fields renders the usage section with no error |
| T-LF2 | Item 3: the search response parses with the schema the route exports; a contract test fails when a client schema differs from its route's |
| T-LF3 | Item 14: OSS → the named Enterprise state; an outage → "LiteLLM unavailable" |
| T-LF4 | Items 4, 5: an app team with no LiteLLM team is absent from the dropdown and the table |
| T-LF5 | Item 15: no linked-account column; the detail shows it |

**Spec:** Design System — the LiteLLM users and teams tabs (D-LF3, D-LF4);
LiteLLM spec — the audit read's edition state (D-LF2).

### ST1 — Settings and small UX

- **D-ST1 (item 1).** The root `pnpm dev` runs a small script that prints
  `Local: <NEXT_PUBLIC_APP_URL>` (with the base path) and then starts
  `next dev`. Next's own line stays; it cannot be changed. The script
  reads `process.env` directly (Rule 50.2's exception for `scripts/**`).
- **D-ST2 (item 6).** The identity pickers of Identity links and Person
  become a search box: at least 2 characters, debounced, at most 10
  results, by name, email or UPN, through `GET /api/identities/directory`
  with a new `q` parameter (Zod, 1–100 characters). Same callers as today
  (admin, org-admin, auditor); a lead still gets no people search (D37).
- **D-ST3 (item 11).** **Refresh now** on Settings → Sync reloads the sync
  status and clears the dashboard's cached usage data
  (`POST /api/sync/refresh`: `internal-admin`, `403` before parsing,
  audited, at most once a minute — a second call inside the minute is
  `429`). It does **not** start a collection: the collector is Phase 6.
  The button says what it does: "Reload the latest collected data".
  Open with the user (Q12).
- **D-ST4 (item 12).** After **Test connection**: a green check and
  "LiteLLM connection is ok", or a red cross and the error, with the icon
  and the text both (never colour alone), in an `aria-live` region.
  `LLM_LENS_LITELLM_BASE_URL` is added to `env.ts` (optional URL, default
  `http://localhost:4000`). It is the value **offered** in the Base URL
  field when no connection is saved; it is never saved by itself, and the
  allowed-hosts rule is unchanged, so `localhost` is still refused where
  it is not allowed (production).
- **D-ST5 (item 13).** In Add account, **Department ID and Team ID are no
  longer typed**: the form asks for the names (or picks an existing
  department or team), and the server generates the ids (a slug of the
  name, made unique). **Account ID stays typed**: it is the 12-digit AWS
  account number of the account whose cost is collected, so the back end
  cannot invent it; the field is labelled "AWS account ID" (confirmed by the
  user, 2026-11-18: "Yes, keep it typed"). The worker checks Add user and Create team: any id a person
  types there today becomes server-generated the same way; if none is
  typed, it records that and changes nothing.
- **D-ST6 (item 17).** **Export access review (CSV)** moves to the header
  of Manage → Audit, as a secondary button (one filled primary per view,
  Rule 40.9). The section at the bottom keeps its content.

**Owns:** `scripts/dev.mjs` and the root `dev` script; `env.ts` (one
variable); `components/settings/SyncTab.tsx`, `SyncStatusPanel.tsx`,
`AccountForm.tsx`, `AccountDialogs.tsx`,
`litellm-panel/LiteLLMConnectionSection.tsx`,
`access/IdentityLinksSection.tsx`, `IdentityLinkSuggestions.tsx`;
`components/manage/AuditPageContent.tsx`; `app/api/accounts/**`;
`app/api/litellm/connection/**`; `app/api/identities/directory/route.ts`
(the `q` parameter); a new `app/api/sync/refresh/route.ts` with its
registry entry; their tests; `e2e/settings-*.spec.ts`.

| Test | Proves |
|---|---|
| T-ST1 | Item 1: the script prints the URL with the base path |
| T-ST2 | Item 6: `q` under 1 or over 100 characters → `400`; at most 10 results; a lead → `403` |
| T-ST3 | Item 11: not admin → `403` before parsing, one `denied` record; second call in a minute → `429`; the tags are revalidated |
| T-ST4 | Item 12: success and failure states with icon and text; the default is offered and not saved; a host outside the allowlist is still refused |

**Spec:** Design System — Settings (Sync, LiteLLM connection, Accounts),

### US1 — The users table

- **D-US1 (item 8).** Manage → Users opens with the People table. The
  search box is inside the People panel (the LiteLLM users page is the
  pattern); the separate search section goes.
- **D-US2 (item 9).** Columns gain **Created** (the identity's
  `createdAt`, UTC, shown as a date).
- **D-US3 (item 10).** Sorting is done by the API:
  `GET /api/identities/directory?sort=<name|email|createdAt|updatedAt|team>&dir=<asc|desc>`
  (Zod enums; default `name`, `asc`). The route reads the identities
  (bound: 2,000; over it the response says `truncated`), sorts in memory
  with a stable tie-break on `oid`, then pages (25 rows). In-memory
  sorting is the project's precedent for bounded lists (Rule 20.7). The
  cursor encodes the sort, so a cursor from another sort is `400`.
  Authorization data is still read per request and never cached.
- **D-US4.** One shared header component, `SortableHeader`, in
  `components/tables/` (new folder): a button in the header cell,
  `aria-sort` on the `th`, the sort in the URL (nuqs). SRT1 reuses it.
- **D-US5.** Each row's name links to `/dashboard/manage/users/[oid]`
  (US2's page).

**Owns:** `components/manage/users/UsersPeoplePanel.tsx`,
`app/dashboard/manage/users/page.tsx`, `components/tables/**`,
`app/api/identities/directory/route.ts`, the module that builds its rows,
the directory schemas in `packages/shared`, their tests,
`e2e/manage-users.spec.ts`. **Shared, one mount line each:** SYNC1 adds
its sync button and its "Not signed in yet" panel to the page.

| Test | Proves |
|---|---|
| T-US1 | Each sort key, both directions, with ties; an unknown key or direction → `400`; a cursor from another sort → `400` |
| T-US2 | Paging through a sorted list returns every identity once |
| T-US3 | `aria-sort` follows the URL; the search is inside the People panel; Created is shown |
| T-US4 | Roles: admin, org-admin, auditor read; a lead → `403` (unchanged) |

**Spec:** Design System — Management → Users; Data Model — *API Routes*
(the directory's `sort`, `dir`, `truncated`).

### US2 — The user page

- **D-US6 (item 16).** `/dashboard/manage/users/[oid]` shows one person:
  name, email, UPN, how they sign in, created and last sign-in; linked
  accounts (usage identities and the LiteLLM link); team and role.
  One new read, `GET /api/identities/[oid]` (admin, org-admin, auditor;
  an unknown `oid` is `404`).
- **D-US7 — every edit uses a route that exists**, with that route's own
  rules: unlink (`DELETE …/litellm-link`), reset spend (RS1's dialog),
  move or remove the team membership, grant or revoke lead, and global
  roles (an `internal-admin` only, never one's own). The page adds no
  permission; a caller sees only the actions they may use.
- **D-US8 — name and email.** For an SSO person they come from Entra at
  every sign-in, so they are shown read-only with that note. For a
  password user the **name** is editable. The **email** of a password
  user is their sign-in key and is not editable: remove and add the user.
  Open with the user (Q11).
- **D-US9.** No LiteLLM write beyond the kept operations (reset, budget);
  the page never adds or removes a LiteLLM user or team member.

**Owns:** `app/dashboard/manage/users/[oid]/**`, a new
`components/manage/users/detail/**`, `app/api/identities/[oid]/route.ts`
with its registry entry, the name edit in the password-user route if it
is missing, their tests, `e2e/manage-user-page.spec.ts`.
**Does not touch:** `UsersPeoplePanel.tsx` (US1 adds the link).
**Security review at the merge** (a new read of one person's access).

| Test | Proves |
|---|---|
| T-US5 | The read: admin, org-admin, auditor `200`; lead `403`; unknown `oid` `404`; no credential, hash or secret in the body |
| T-US6 | Each action appears only for a caller who may use it; own roles cannot be edited |
| T-US7 | SSO name and email are read-only; a password user's name edit is audited |

## 5. Orchestration

Each unit runs as a workflow when the user opts in in the worker session
(`worker_prompt.md` §4): Red (test engineers, in parallel on disjoint test
files), Green (developers, in parallel on disjoint files), Fix, Gate. The
design per unit is in the planner's package, `workflows.md`. At most 3
agents at once per unit here; sonnet for tests and code, haiku for gate
runs; no review agents (Rule 70.12). The usage tiers of `worker_prompt.md`
apply.

## 6. Guards

- Never weaken a test or a permission. Never commit to `main`, push,
  deploy, or bypass a hook.
- `env.ts`, `packages/shared` and `components/ui/**` are shared: a change
  there means the full suite and the full e2e at the unit's gate
  (Rule 70.12).
- No raw hex, no new package, no global state library (Rule 40). Icons
  from Lucide. Status never by colour alone.
- Every new Route Handler registers in `test/route-registry.ts`
  (Rule 60.23).
- A question in §7 is built with its default; do not wait for the answer.
